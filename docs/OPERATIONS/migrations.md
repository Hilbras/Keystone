# Database migrations

§6.5. How a schema change is generated, applied, verified and rolled back — and
what Keystone now refuses to do.

Drizzle migrations are **forward-only**. There is no `.down.sql`, no
`drizzle-kit down`, and no per-migration rollback. That is a property of the tool,
not an oversight, and this document describes the strategy that follows from it
rather than pretending otherwise.

The three commands:

```bash
npx @hilbras/keystone migrate            # apply pending migrations
npx @hilbras/keystone schema:verify      # assert every expected table exists
npx @hilbras/keystone migrate --verify   # apply, then verify
```

From a source checkout the same commands are wrapped:

```bash
scripts/migrate.sh up
scripts/migrate.sh verify
scripts/migrate.sh up --verify
scripts/migrate.sh rollback --dump /backups/keystone-20261020T000000Z.dump
```

---

## 1. Where migrations live and how they run

| Path | `src/db/migrations/*.sql` (+ `meta/_journal.json` and snapshots) |
|---|---|
| Generated by | `npm run db:generate` (drizzle-kit, from `src/db/schema.ts`) |
| Applied by | `drizzle-orm/postgres-js/migrator` |
| Shipped in the package | `dist/db/migrations/` (copied by `npm run build`) |
| Shipped in the image | yes (`COPY . .` in the builder stage) |

Migrations are applied in **three** places, deliberately:

1. **At server startup** — `src/index.ts` runs `migrate()` before `listen()`, so a
   fresh container comes up with a usable schema.
2. **The CLI** — `keystone migrate`, for a deploy pipeline that wants the schema
   applied before any instance starts.
3. **The setup wizard** — `POST /setup/migrate`, for a first install.

All three read the same folder. Since 3.11.0, startup also **verifies** the schema
immediately after migrating (see §3).

> Two instances starting at the same time both run `migrate()`. Drizzle's migrator
> takes an advisory lock on its journal table, so one waits for the other; this is
> the same mechanism that made the setup bootstrap race-safe in 3.9.4. It is still
> better to run migrations as a separate deploy step when your pipeline allows it.

## 2. The safety model: up / verify / rollback

### up

Apply what the journal says is pending. Safe to run repeatedly; applied
migrations are recorded and skipped.

### verify

`schema:verify` compares the tables declared in `src/db/schema.ts` with
`information_schema.tables` in the current schema. It uses Drizzle's own
`isTable`/`getTableName`, so a table added to the schema cannot be forgotten in a
hand-maintained list.

It answers the question the journal cannot: *does the database actually match the
application?* The cases it catches are the ones that happen in deployment:

- an interrupted migration (the journal moved, the DDL did not);
- a restore from an older dump;
- a `search_path` that resolves to a different schema.

It is a **presence** check, not a full diff. A column missing from an existing
table still passes. That bound is deliberate — a full diff means shipping a schema
comparison engine, and presence catches the realistic failures.

### rollback

There is no down migration. `scripts/migrate.sh rollback --dump FILE` runs
`pg_restore --clean --if-exists` from a dump and then verifies the result. It is
destructive and requires the file explicitly.

**The rollback you should actually plan for** is a dump taken immediately before
`up`:

```bash
pg_dump -Fc --no-owner --no-privileges -f pre-migrate.dump "$DATABASE_URL"
scripts/migrate.sh up --verify
```

For a change that must be reversible without a restore, use expand/migrate/contract
(§4).

## 3. What happens at startup

Before 3.11.0, a failed migration was logged and the process continued to
`listen()`. A container with the wrong schema answered 500s to every request while
telling the orchestrator it was healthy.

Now:

| Profile | Migration fails | Schema verification fails |
|---|---|---|
| `production`, `staging` | **refuses to start** | **refuses to start** |
| `development`, `test` | logged, serves | logged, serves |

`KEYSTONE_ALLOW_DEV_DEFAULTS=true` restores the old behaviour in a strict profile,
for a deliberate single-node development deployment.

Startup order:

```text
connect Redis (non-fatal)
build the app (routes, workers)
migrate
verify schema          <-- new
startup recovery       <-- new: reclaim/re-enqueue webhook deliveries, scan locks
load signing keys
seed role permissions
configuration validation (fatal findings refuse to start)
install SIGTERM/SIGINT handlers
listen
```

The startup probe (`/health/startup`) answers 503 until `listen()` returns, so a
migration that takes longer than the probe budget does not get the pod killed —
provided `failureThreshold` is large enough. The shipped manifest allows 40 × 10 s.

## 4. Writing a migration that can be deployed safely

### Expand → migrate → contract

For anything that is not purely additive:

**1. Expand.** Add the new column/table with a default or as nullable. Deploy.
Nothing reads it yet, so old and new code both work.

**2. Migrate.** Backfill in batches, and deploy code that writes both the old and
new shape (dual-write) if the old shape is still read.

**3. Contract.** Only after every instance runs code that uses the new shape,
remove the old column/table in a later release.

Never combine "add" and "remove" in one migration. A rolling deploy runs old and
new code at the same time; a migration that removes a column the old code still
reads fails requests during the overlap.

### Dangerous operations

| Operation | Risk | Use instead |
|---|---|---|
| `DROP TABLE` / `DROP COLUMN` | old code still reads it during a rolling deploy | contract step, one release later |
| `ADD COLUMN ... NOT NULL` without a default | rewrites/locks the table; existing rows fail | add nullable, backfill, then set `NOT NULL` |
| Rename | old code breaks immediately | add new, dual-write, backfill, drop old |
| Type change | implicit rewrite and lock | new column + backfill + swap |
| Index without `CONCURRENTLY` | blocks writes for the build duration | `CREATE INDEX CONCURRENTLY` in a hand-edited migration |
| Large backfill in one statement | long transaction, bloat, lock contention | batched updates |
| `UPDATE`/`DELETE` on `audit_log` | destroys the audit trail | never |

Drizzle supports hand-editing a generated `.sql` file; keep the journal and
snapshot consistent with `npm run db:generate` afterwards.

### Generated vs. hand-written

`npm run db:generate` reads `schema.ts` and writes the next `NNNN_name.sql`. Two
rules keep it honest:

1. **Review the SQL.** Drizzle generates what the diff says, not what you meant.
   A renamed column is often generated as drop + add.
2. **A migration file is immutable once released.** Editing one that has already
   been applied produces databases that disagree while both report "up to date".
   Fix forward with a new migration.

## 5. Applying a migration in a deploy pipeline

Recommended order, for a rolling deployment:

```text
1. backup (pg_dump)                      <- your only real rollback
2. apply migrations as a one-shot job     <- not from every replica
3. verify the schema                      <- schema:verify
4. roll out the new application version
5. watch /health/ready and the error rate
```

If the pipeline cannot run a separate job, the startup path is safe but slower:
every replica runs `migrate()` behind the journal's advisory lock, and a failure
stops the replicas instead of leaving them half-serving.

Do **not** run `migrate` and `rollback` concurrently with live traffic. `rollback`
drops the schema.

## 6. Troubleshooting

| Symptom | Cause | Action |
|---|---|---|
| `Refusing to start after a failed migration` | bad SQL, insufficient privileges, unreachable DB | fix the cause, run `scripts/migrate.sh up --verify` by hand |
| `Schema verification failed: N table(s) missing` | interrupted migration, stale restore, wrong `search_path` | inspect `missing` in the log; re-run `up`; if it persists, restore |
| `relation "..." does not exist` at runtime but startup passed | a column-level change, or an object outside the table list | inspect the query; presence checking is bounded (§2) |
| `keystone migrate` hangs | it opens a pool and Redis; the CLI releases both on exit | update the CLI; this was fixed in 3.5.0 (`withReleasedConnections`) |
| Migration applies but the app behaves as before | two schemas in `search_path`; the migration ran in the other one | set `search_path` explicitly and re-verify |
| Rollback fails with `role "..." does not exist` | dump was taken without `--no-owner` | restore with `--no-owner --no-privileges` |
