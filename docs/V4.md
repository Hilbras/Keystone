# Keystone v4

**What v4 is.** A version number is a promise about what will not change.
Keystone v4 makes that promise explicit: seven contracts are snapshotted and
gated, the breaking changes are written down, and the deployment and
operational behaviour is documented rather than implied.

v4 does not add a feature. It declares one.

---

## The guarantees

Each of these is a claim, and each has the place it is proven. A guarantee
without evidence is a slogan.

### Distributed correctness

| Guarantee | Proven by |
| --- | --- |
| A job, a webhook delivery, a token rotation, a setup bootstrap and a lock are each owned by exactly one worker, across any number of instances | `src/tests/chaos/concurrency.test.ts`, `src/tests/security/webhooks/atomicDeliveryClaim.test.ts`, `src/tests/security/setup/bootstrap-race.test.ts` |
| A worker that dies holding work does not strand it | `src/tests/chaos/worker-crash.test.ts` |
| A rate limit is one budget across the fleet, not one per instance | `src/tests/chaos/redis-failure.test.ts` |
| A database that cannot be reached does not become an unbounded server | `src/tests/chaos/redis-failure.test.ts`, `src/tests/chaos/db-failure.test.ts` |
| Every upgrade path ends in the same schema a fresh install has | `src/tests/deployment/migrationAudit.test.ts` |

### Security

| Guarantee | Proven by |
| --- | --- |
| A replayed refresh token ends the credential it belongs to, and only that | `src/tests/security/tokens/refreshTokenReplay.test.ts` |
| A stolen token cannot be routed around by choosing a different endpoint | `src/tests/security/tokens/refreshTokenReplay.test.ts` |
| A failure says what it is — 400, 401, 403, 404, 409, 429, 503 — and never leaks a query, a parameter or a stack | `src/tests/chaos/db-failure.test.ts`, `src/tests/errorContract.test.ts` |
| A webhook cannot be pointed at a private address, and a redirect is not followed | `src/tests/security/webhooks/ssrf-redirect-and-schemes.test.ts` |
| A credential in a query string is not in a log | `src/tests/security/…` — see the registry entry for the query-string drop |

### Operational

| Guarantee | Proven by |
| --- | --- |
| An operator can tell liveness from readiness from startup | `src/tests/observability/health.test.ts` |
| A shutdown is ordered, bounded, and exits with a code that means something | `src/tests/deployment/gracefulShutdown.test.ts` |
| A deployment that is misconfigured refuses to start, and says which setting | `src/tests/deployment/configurationValidation.test.ts` |
| A release is validated from the outside, as a published artifact | `scripts/verify-release-candidate.mjs`, `scripts/verify-release-artifacts.mjs` |

### API stability

Seven contracts are snapshotted in
[`docs/contract-freeze.json`](contract-freeze.json) and gated by
`npm run verify:contract`:

| Contract | What is frozen |
| --- | --- |
| REST API | Every path, method and tag |
| OAuth behaviour | The discovery metadata and the error codes |
| Token format | The claims, the algorithm, the audience, the issuer |
| Database contracts | The tables, their columns, their nullability and defaults, the migration set |
| Webhook format | The headers a delivery carries, the shape of its body |
| SDK interfaces | What each published package exports, and where it points |
| Configuration | The environment variables the server reads |

A change to any of them fails the gate with the exact difference, and the only
way past it is to update the snapshot on purpose, in the same commit, where a
reviewer sees it. See [The frozen contracts](CONTRACTS.md).

## What changed in v4

The changes are listed in full, with the migration steps, in
[the v4 migration guide](MIGRATION-4.0.md). In short:

- a schema violation answers **400** and a database outage answers **503**,
  where both answered 500;
- a replayed refresh token revokes the credential **family** rather than the
  account;
- the error bodies carry a stable `code` and a `requestId`.

**3.x broke things without writing them down.** The 3.0.0 → 3.14.0 range
contains at least a dozen client-observable breaks and no `BREAKING:` block
anywhere in its changelog. The v4 guide covers them retroactively, because a
consumer upgrading from 3.0.0 meets all of them.

## Deployment

```bash
npm install @hilbras/keystone@4.0.0
```

Node 26 or later. PostgreSQL 16 or later, Redis 7 or later. See
[Deployment](../README.md#deployment) and
[Running Keystone on more than one instance](multi-instance.md).

Before the rollout:

```bash
npx @hilbras/keystone migrate --verify
```

The migration is additive — no column is dropped and no data is rewritten — and
it is safe to run ahead of the rollout. For a production deployment, set
`KEYSTONE_QUEUE_PROVIDER=bullmq`, `COOKIE_SECURE=true`, a strong TOTP key and
`KEYSTONE_ENCRYPTION_KEY`; the server refuses to start otherwise, and says
which setting is at fault.
