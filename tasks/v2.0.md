# v2.0.0 Security Architecture 2.0

Authoritative scope: `plan.md` Phase 4 (v2.0.0). Major release.

## Status

- [x] Remove trust in arbitrary identity headers
- [x] Explicit trusted-proxy configuration
- [x] Service account identity only from a validated certificate or authenticated credential
- [x] Proxy security: trusted ranges, header stripping, header/cert validation
- [x] Security boundary documentation
- [x] Breaking changes documented with migration instructions

## Findings

Two issues were exploitable in 1.9.0, not merely theoretical:

1. **`x-service-account-id` was a complete authentication bypass.** It resolved
   a service account on its own, with no certificate and no credential. Anyone
   who could reach Keystone and knew or guessed an account ID became that
   account. `requireMTLS` was not wired to any route, but it was exported plugin
   surface, so any consumer using it inherited the bypass.
2. **`trustProxy: true` plus an unconditional `x-forwarded-for` read.** Any
   client could present a fresh address per request and never hit a rate limit,
   including against login, password reset, MFA verification, and SCIM.

## Changes

- `src/services/trustedProxies.ts` — new. `KEYSTONE_TRUSTED_PROXIES` parsing,
  IPv4 CIDR and IPv6 prefix matching, IPv4-mapped normalization, peer vs.
  forwarded address resolution, fingerprint validation.
- `src/plugins/headerSanitization.ts` — new. `onRequest` hook stripping identity
  headers from untrusted peers, registered before every plugin and route.
- `src/plugins/mtls.ts` — rewritten. Certificate-only identity, lookup by
  bound fingerprint, hint cross-checking, fingerprint validation, distinct
  untrusted-peer vs missing-certificate responses.
- `src/plugins/rateLimit.ts` — limiter keys on the unspoofable address.
- `src/db/schema.ts` — `service_accounts.cert_fingerprint` (unique, partial) and
  `service_accounts.revoked_at`.
- `src/services/serviceAccounts.ts` — certificate binding and revocation, with
  canonicalization enforced in the service rather than only at the route.
- `src/routes/serviceAccounts.ts` — certificate binding and revoke endpoints.
- `src/config.ts`, `src/index.ts`, `src/setup-server.ts` — `trustProxy` derived
  from the trusted-proxy list.
- `docs/security/{trust-boundaries,proxy-security,mtls}.md`, `docs/MIGRATION-2.0.md`.

## Regression verification

Both headline fixes were confirmed against the real pre-fix code, not just
asserted in the abstract:

- Reverting `clientIdentifier` to the old `x-forwarded-for` read **and**
  disabling the stripping hook reproduces the bypass (`200,200,200,200,200`) and
  fails `counts every spoofed address against one budget when no proxy is
  trusted`. Reverting only one layer does not fail, because the other still
  blocks it — the fix is two independent layers.
- Restoring the 1.9.0 `src/plugins/mtls.ts` from git fails
  `rejects x-service-account-id alone, with no certificate` with
  `naming a service account must never authenticate`.

## Defects found while building this

- `normalizeAddress` did not handle the hex form of IPv4-mapped IPv6
  (`::ffff:7f00:1`), so a mapped peer could slip past an IPv4 allowlist.
- `config` is a load-time snapshot, so the trusted-proxy cache never observed a
  changed value. The setting is now read at call time and cached on the raw
  string.
- `setServiceAccountCertificate` originally did not canonicalize; canonicalizing
  only in the route's Zod schema let a direct service caller store two spellings
  of one certificate as two bindings. Caught by a test, then moved into the
  service.
- The SCIM token-hash unique indexes from 1.9.0 were in the Drizzle schema but
  never migrated. Migration `0015` creates them.
- `docs/DEPLOYMENT.md` documented `$proxy_add_x_forwarded_for`, the append form
  that lets a client prepend a forged address. Corrected.
- The `isInfrastructureAddress` IPv6 check skipped fully expanded addresses
  (`fe80:0000:...:0001` has 8 hextets). Caught by extending its own test.
