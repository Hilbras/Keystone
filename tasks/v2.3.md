# v2.3.0 Session & Password Recovery Hardening

Authoritative scope: `plan.md` Phase 7 (v2.3.0). Minor release.

## Status

- [x] After password reset: revoke refresh tokens, invalidate sessions, invalidate other recovery credentials
- [x] Centralized revocation: revokeUserSessions / revokeRefreshTokens / revokeAuthenticationSessions
- [x] Session invalidation on reset, and MFA enablement routed through the same layer
- [x] Recovery credentials: random, hashed at rest, single-use, short-lived, rate-limited, audited — already sound, verified
- [x] No account enumeration through recovery responses — already sound, verified

## The finding

**Completing a password reset did not remove existing access.** It changed the password and left every session, every refresh token, and every other outstanding reset token working.

A password reset is the standard response to a suspected compromise, so this defeated its own purpose: an attacker who triggered the reset kept their session and their access, while the victim believed they had locked the intruder out.

`revokeAllUserRefreshTokens` existed and was called from exactly one place — `routes/totp.ts`, on MFA enablement. The reset path never called it. The cause was structural: revocation was open-coded per call site, so nothing required a new call site to include it.

## Fix

`src/services/sessionRevocation.ts` — one layer, with the plan's three named operations plus the one recovery needs:

- `revokeRefreshTokens(userId, options?)`
- `revokeAuthenticationSessions(userId, options?)`
- `revokeRecoveryCredentials(userId)`
- `revokeUserSessions(userId, options?)` — sessions + refresh tokens, the composite most changes want
- `revokeAllUserCredentials(userId, options?)` — plus recovery credentials, used after a reset

A successful reset now invalidates all three. The MFA-enablement path was rerouted through `revokeUserSessions` so the rule cannot drift between the two.

`options.exceptSessionId` / `exceptRefreshTokenId` exist for a change the user makes to their own account. They are deliberately documented as unsafe on a reset the user did not initiate, because the current session is exactly what an attacker would be holding.

## Deliberate exclusion: API keys

API keys are **not** revoked by a password reset. They are separately issued, long-lived credentials belonging to integrations rather than to the person, and silently invalidating them breaks deployments without improving the account's own security.

The residual gap is real and is documented in `docs/SECURITY.md`: a key minted by an attacker who already held the password survives recovery. The right fix is key expiry and rotation, not coupling key lifetime to a human's password. The deactivation path (`repositories/user.ts`) does revoke API keys, because there the account is gone rather than recovered.

## Already sound, verified rather than assumed

| Requirement | Status |
| --- | --- |
| Cryptographically random | 384-bit `crypto.randomBytes` |
| Hashed at rest | SHA-256 digest only |
| Single-use | Since v2.2.0 |
| Short-lived | 1 hour |
| Rate-limited | 5 per 15 minutes on `/auth/forgot-password` |
| Audited | `password_reset_requested`, `password_reset_completed` |
| No enumeration | Both the found and not-found paths return `{ success: true }` |

## Regression verification

Removing only the revocation call from the reset path — leaving the reset itself working, which is the pre-2.3.0 state:

| Assertion | Result |
| --- | --- |
| `kills the attacker's session and refresh token` | `no session may survive a password reset` |
| `does not let a token issued before the reset be used afterwards` | `the intercepted earlier token must be dead` |
