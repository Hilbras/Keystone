# v2.4.0 OAuth 2.0 / OIDC Security Hardening

Authoritative scope: `plan.md` Phase 8 (v2.4.0). Minor release, with one
breaking change (client authentication on the authorization code grant).

## Status

- [x] Authorization code atomic consumption — already atomic, now covered by a concurrency test
- [x] PKCE enforced for public clients; dead bypass branch removed
- [x] Effective scopes = registered ∩ requested ∩ consented
- [x] Strict redirect URI matching
- [x] OIDC nonce sent and validated
- [x] ID token validation: issuer, audience, signature, expiration, issued-at, subject, algorithm pinned
- [x] Refresh token context: client, org, auth context, and scopes all persisted and validated

## Findings

| # | Finding | Status |
| --- | --- | --- |
| 1 | `authorization_code` grant never called `verifyClientSecret` | **Live.** RFC 6749 §3.2.1 violation |
| 2 | Redirect URI registration used `z.string().url()`, accepting `javascript:` / `data:` | **Live** |
| 3 | OIDC federation sent no nonce and verified none | **Live** |
| 4 | ID token: algorithms inferred, `exp`/`iat`/`sub` not required | **Live** |
| 5 | Requested scopes stored verbatim; only consent filtered them | **Live**, cosmetic today |
| 6 | `verifyPKCE` returned true when no challenge was registered | **Latent** — `/authorize` already required a challenge |
| 7 | Token endpoint tolerated `redirect_uri IS NULL` | **Dead code** — `redirect_uri` is required at `/authorize` |

### On findings 6 and 7

Both looked alarming and neither was exploitable. `AuthorizeQuerySchema` already
required `code_challenge` and `code_challenge_method`, so `record.challenge` was
never null and the `!challenge → true` branch was unreachable. `redirect_uri` is
also required at `/authorize`, so the stored value was never null either.

They were still fixed, because a branch that returns "valid" when it has nothing
to check is a trap for the next person who makes the field optional. Recorded
here so the distinction is not lost: 1–5 were live, 6–7 were not.

### Scopes are cosmetic today

`requireScopes` in `src/plugins/auth.ts` applies to **API keys only**. An OAuth
access token's authority comes from the user's membership and permissions, not
from its scope strings. So finding 5 was not directly exploitable — a client
could put any string in its token and gain nothing. It is fixed anyway, because
the moment anyone wires scope enforcement to OAuth tokens, an unconstrained scope
string becomes privilege escalation, and that is not the moment to find out.

## Fixes

- `src/services/redirectUri.ts` — registration validation and exact matching in
  one module, used by both the admin API and `/authorize`.
- `verifyPKCE` takes `requireChallenge`; the accept-on-nothing branch is gone;
  comparison is constant-time via `crypto.timingSafeEqual`.
- `requiresPkce(clientSecretHash)` — a secretless client must use PKCE.
- `resolveEffectiveScopes` — the intersection, refusing rather than dropping.
- `findConsent` — exposes the granted set, which `hasConsent` only summarized.
- `client_type` and `allowed_scopes` on applications; `client_secret_hash`
  nullable, with a check constraint keeping a public client secretless.
- `scopes` on `refresh_tokens`, carried across rotation.
- OIDC connector: nonce parameter, nonce verification, pinned algorithms,
  required claims. Route: `oauth_nonce` httpOnly cookie, and a callback without
  one is refused.

## Regression verification

| Reverted | Result |
| --- | --- |
| Client authentication at the token endpoint | `expected the grant to be refused, got 200` |
| Nonce issuance in the federation start route | `expected an oauth_nonce cookie` |

The first is the important one. The test uses a **correct** PKCE verifier, so the
client secret is the only missing factor — without client authentication the
grant returns 200 with a full access token, which is the vulnerability stated
plainly rather than inferred from a status code.

The nonce test's limit is documented in the test itself: it catches a route that
stops issuing a nonce, not one that sets the cookie and forgets to pass it on.
That narrower gap needs a connector stub in the route, which is more machinery
than it justifies.
