# v2.6.0 Service Accounts, API Keys & Permission Scopes

Authoritative scope: `plan.md` Phase 10 (v2.6.0). Minor release, with a breaking
change to API key scope names.

## Status

- [x] Authentication lifecycle: authenticate -> org -> membership -> principal -> authorize
- [x] Centralized API key scope registry
- [x] Effective scopes = granted ∩ principal authority
- [x] API key security: hash, prefix, expiry, rotation, revocation, last-used, audit, scope enforcement
- [x] Service account security: rotation, revocation, expiry, permission boundaries, audit, org isolation

## Findings

| # | Finding | Exploitable today? |
| --- | --- | --- |
| 1 | The scope guard honoured a `"service_account"` wildcard — a key holding that string satisfied every requirement, and the string was client-suppliable | Not reachable: see below |
| 2 | The same guard failed open when `apiKeyScopes` was absent | Not reachable |
| 3 | `requireScopes` was defined, decorated, and referenced by **zero** routes | Not reachable |

### Why "not reachable" is the honest answer

`app.authenticate` is JWT-only — it returns 401 for anything that is not a valid
access token. `authenticateOrApiKey` is the handler that contains the API key
path, and before this release exactly one route used it: `GET /auth/validate`.

So a leaked API key reached one endpoint, returning the caller's own public
profile. The defect is real — a credential whose stated limits were fiction — but
it is not an authentication bypass, and calling it one would misdirect anyone
prioritising the work.

This is stated plainly in `tasks/v2.6.md` and the changelog rather than left for a
reader to discover.

## What the phase delivers

The enforcement machinery, so the next route to adopt key authentication inherits
a real check rather than re-deriving one.

- `src/services/scopes.ts` — the registry. Canonical names, descriptions,
  per-principal defaults, validation, and an allow-list grant check. A scope not
  in the registry cannot be granted, so there is no string a caller can invent.
- `requireScopes` fails closed, keyed on a new `request.apiKeyId` that is set only
  when a machine credential authenticated. A session is still exempt, because it
  carries a person's authority and is governed by the permission system.
- Applied to API key create/list/revoke, session list/revoke, and profile
  read/write.
- Unknown scopes refused at creation with a `400` listing what was rejected and
  what is allowed, rather than stored verbatim or silently dropped.
- `profile:read`, `profile:write`, `mfa:manage` are human-only.
- `src/plugins/machinePrincipal.ts` — `requireHumanPrincipal`, applied to TOTP,
  WebAuthn, SMS OTP, identity linking, OAuth consent, and userinfo.

## Plan item 1 — the lifecycle ordering bug I introduced

`requireHumanPrincipal` reads `request.serviceAccount`, which is populated by
`app.authenticate`. My first pass inserted the guard *before* `app.authenticate`
in the `preHandler` array, so it would always have seen `undefined` and never
refused anything — while looking correct.

That is precisely the failure plan item 1 names: authorization happening before
the identity context it depends on is available. Caught by reading the generated
`preHandler` rather than trusting the edit, then fixed to sit immediately after
`app.authenticate`. Every placement is commented with the reason it is there.

## Two design errors the tests caught

- I gave service accounts a default of `profile:read`. Their "profile" is a
  synthesized object with an id of `sa:<uuid>` matching no user row, so the scope
  is meaningless for a machine and misleading in an audit log. Profile scopes are
  now human-only and the service-account default is `organizations:read`.
- I first wrote HTTP tests against the API key routes, which are JWT-only, so
  they asserted 403 and got 401. The tests were rewritten against
  `GET /auth/validate`, the one key-reachable route, which is where enforcement
  is genuinely observable.
