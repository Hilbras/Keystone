## The denylist measurement

Rather than assert that the denylist was incomplete, I ran it against 24
secret-looking names. Twelve came back unredacted:

```
SIGNING_KEY  JWT_SIGNING_KEY  SMTP_USER  TWILIO_AUTH  SENDGRID_KEY
PROVIDER_APIKEY  SAML_CERT  TLS_KEY  CERT_PRIVATE  HMAC_KEY  KMS_KEY  DB_URL
```

`SIGNING_KEY` and `JWT_SIGNING_KEY` are the significant ones: the admin
configuration endpoint was returning the JWT signing material in the clear. The
12-character `SMTP_USER` is a false positive in the other direction — a username
is not a secret — which is why the replacement is an explicit allowlist rather
than a broader regex.

## Webhook secrets: encrypted, not hashed

The plan offers a choice. Hashing is the usual answer for a stored credential,
but it is not available here: Keystone *signs* outbound payloads with the secret,
so it must be able to recover the plaintext. A hash would make signing
impossible. Since the plaintext has to be recoverable, recoverable secrets are
precisely the ones that must be encrypted at rest.

`decryptSecret` already provided a versioned AES-256-GCM envelope — but it
**throws** on anything that is not an encrypted envelope, offering a legacy *CBC*
form rather than a plaintext fallback. Delegating to it would have thrown on the
first delivery for every pre-existing endpoint. `readWebhookSecret` therefore
detects the envelope itself and returns anything else unchanged. Verified: the
round trip is exact, signature output is byte-identical, and a pre-upgrade
plaintext secret reads back unchanged.

## The test bug worth recording

The CORS tests were initially written against a *copy* of the origin predicate
rather than the server's, because the predicate lived inline in `index.ts` and
bootting the application per `NODE_ENV` is slow. That is a test that passes while
the code it is meant to protect is reverted — the same tautology I have hit
before in this project.

Fixed by extracting `isOriginAllowed` into `src/services/trustedProxies.ts`,
shared by both servers, and importing it. Reinstating the allow-all-on-empty
behaviour now fails three tests.

## Two of my own assertions were wrong

- I asserted that no allowlist entry trips the legacy denylist regex. Five do:
  `SETUP_TOKEN_URL`, `RESET_PASSWORD_URL`, `KEYSTONE_SECRETS_PROVIDER`,
  `ACCESS_TOKEN_TTL_SECONDS`, `REFRESH_TOKEN_TTL_SECONDS`. None is a credential;
  the regex matches `TOKEN` inside `ACCESS_TOKEN_TTL_SECONDS`. The allowlist is an
  independent judgement and does not have to agree with an over-broad legacy
  heuristic, so the test now asserts against the real credential list instead.
- The setup-token logging test read the `.ts` source from `dist/`, where only
  `.js` exists. Rewritten behaviourally: a rejected token must produce no output
  at all. That is a better test anyway — it asserts behaviour rather than source
  text.
