# v2.8.0 Rate Limiting, Proxy Security & Abuse Prevention

Authoritative scope: `plan.md` Phase 12 (v2.8.0). Minor release.

## Status

- [x] Redis failure: distributed limiter plus a bounded local emergency limiter
- [x] Strong limits on all nine named sensitive endpoints, plus API key creation
- [x] X-Forwarded-For never trusted blindly — delivered in v2.0.0, verified here
- [x] Proxy spoofing tests: spoofed XFF, multiple values, direct, trusted, untrusted, IPv4, IPv6
- [x] Abuse events: rate limit, invalid credentials, token replay

## Findings

| # | Finding | Severity |
| --- | --- | --- |
| 1 | A Redis outage removed rate limiting **entirely** | High — the worst possible moment to lose the control |
| 2 | MFA verification shared one budget across every user behind an address | High — self-inflicted lockout |
| 3 | Second-factor management shared one budget per address | Medium — same cause |
| 4 | Credential spraying was unbounded | Medium |
| 5 | A refused request left no record at all | Medium — guessing was invisible |
| 6 | `user_login_failed` existed in the vocabulary and was never emitted | Medium |
| 7 | A replayed refresh token was indistinguishable from an unknown one | Medium |

Items 3 and 4 of the plan (X-Forwarded-For, proxy spoofing) were delivered in
v2.0.0. This phase verifies them with tests rather than re-implementing them.

## Item 1 in detail

`isAllowed()` returned `true` whenever `isRedisReady()` was false. So during an
outage, `login`, `mfa/verify`, `sms-otp/verify` and the OAuth token exchange had
no limit at all. An outage is exactly when unlimited attempts are worth having —
it is the moment a burst of guessing does not look like a burst.

`src/services/localRateLimit.ts` is a bounded in-process fallback. It is
strictly weaker than the distributed limiter: a client gets one budget *per
instance*, so a fleet multiplies the allowance. That is a degradation worth
having. Unbounded is not.

The store is capped at 10,000 keys. An unbounded map keyed by client address is
itself a denial-of-service vector — rotating addresses would grow it without
limit — so expired windows are swept and the oldest are evicted at the cap.
Eviction only ever forgets an already-expired window, so it grants no extra
budget; there is a test for that.

## The suite that was not testing what it appeared to

`mfa.test.ts` never *connected* Redis. It imported the client in teardown to
quit it, and nothing ever opened the connection — `lazyConnect` means the limiter
was never running for that suite. It passed **only because the limiter failed
open**, which is the behaviour this phase removes.

Connecting Redis took the suite from green to 12 failures, and those failures
were the useful output: they exposed two real keying defects that fail-open had
been concealing. Fixing the keying took it to 55/55.

This is the third time in this project that a test passed for the wrong reason,
and the pattern is consistent — a test that does not exercise the real path.

## Item 5 in detail

A rate-limit trip produced a `429` and nothing else. `rate_limit_triggered` now
records the endpoint, the client address, and **which limiter decided**.
`redis`, `local`, and `none` are distinct operational situations: a degraded
in-process control is a reason to go and look at Redis, and recording it as if it
were the healthy path would hide exactly that.

## Four defects the failing suite exposed

1. **MFA keying** — `mfa-verify:<address>:<body.email>`, and that endpoint does
   not carry an email, so every verification from one address shared 20 attempts.
   Now keyed on the challenge, which identifies one login attempt.
2. **TOTP keying** — 10 attempts per address for authenticated routes. Now per
   user, which is the right unit since a TOTP code is checked against one
   account's secret.
3. **Login spraying** — keyed on address *and* address, so varying the submitted
   address gave a fresh budget per attempt. Added a second address-keyed budget.
4. **API key creation had no limit at all** — minting a credential is an
   authentication event.

## Tests corrected rather than forced

Four of my own assertions were wrong before the code was:

- A zero-length window does not reset an *existing* window; the test assumed it
  did. Rewritten to use a fresh key.
- The "sensitive endpoints are opted in" check used `require` in an ESM test, and
  did not understand limiters built by a factory (`factorRateLimit`), so it
  reported the TOTP routes as missing when they were covered. It now handles both
  forms.
- The `rate_limit_triggered` test expected a `429` from a limiter configured
  without the emergency flag — which fails open when Redis is down, so it never
  refused anything. The test now sets the flag, with a comment explaining why.
