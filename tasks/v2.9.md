## Item 1: the one that mattered

`node --test` expands `**` as a **single directory level**, not as globstar. When
the security suites gained a directory level, the discovery patterns stopped
matching them. The entire authorization suite — 48 tests — dropped out of the run.

**The run still reported success**, because everything that remained passed. A
green job was reporting on less than the repository contained, and nothing in the
pipeline could tell the difference.

This is the same shape as the other three "test passed for the wrong reason"
findings in this project, and the most dangerous of them, because the others
produced a wrong answer while this one produced a right answer about the wrong
set of files.

The fix is one pattern per directory depth, spelled out, with no overlap — the
first attempt used `**` twice, which re-listed the same files and made two copies
of each suite race on the same rows.

## Item 1: reorganising without losing anything

14 flat files became 16 suites across 14 domains. Verified lossless rather than
assumed: **381 security tests before, 381 after; 430 total before, 430 after.**

Two files were not split, deliberately:

- `proxy/trust-boundary.test.ts` also covers mTLS certificate binding
- `oauth/oauth2-hardening.test.ts` also covers OIDC ID token verification

Splitting is mechanical, but every split copies the whole import header into each
partition, and the resulting churn risks removing a live import. Two attempts at
automating that produced files that did not compile — including one that deleted a
declaration that was genuinely used, because the lint report driving it was stale.
The registry records the mapping instead, which is honest and does not risk the
code.

`tenant-isolation/` was dropped as a directory: SCIM tenant isolation and
organization-scoped SSO are covered inside `scim/isolation.test.ts` and
`oidc/enterprise-sso.test.ts`, and the registry verifies that mechanically. An
empty directory would have implied a suite that does not exist.

## Item 2: making the mandatory list mechanical

A checklist of twelve attack classes in a document is a convention. The plan asks
the pipeline to *test* them. So each registry entry declares which classes it
covers, and `npm run registry:check` fails if any class is uncovered, if an entry
names a test that does not exist, or if a security suite is claimed by no entry.

The last check is the one that stops a suite being deleted quietly: removing
`src/tests/security/saml/sso-endpoint.test.ts` fails the build until somebody
decides, in writing, that it is no longer needed.

The check runs in two places — as part of `npm test` (`registry.test.ts`) and as
a release gate step — so it cannot be skipped by only running the security suite.

The eight Semgrep rules encode defects this codebase actually shipped, including
two that are ordering and completeness problems no general rule can see:

- `requireHumanPrincipal` placed **before** `app.authenticate` sees no service
  account and permits everything. I made that mistake once during this programme
  and only caught it by checking the ordering. A guard that is present, exported,
  called, and inert is invisible to a type checker and to a linter.
- a secret **denylist** where an allowlist is the only correct shape.

Every rule was verified in both directions before being committed, because a
ruleset that has never fired is decoration. Getting there took four iterations: an
unquoted pattern containing `: ` is a YAML mapping error, a `pattern-not-either`
that repeated the positive pattern excludes everything, `{ ... secure: $S ... }`
with spaces is not valid Semgrep, and the first working cookie pattern flagged
`auth.ts` twice because its options are spread from a helper.

## Item 4: secret scanning found nothing, and that is a result

Gitleaks over the **full history** — every commit, not the tip — reports no
leaks. Worth stating explicitly: **no npm token, no signing key and no private key
are in the git history.**

The allowlist that makes this pass covers exactly three literal test passwords
under `src/tests/`, because `generic-api-key` matches any `password: "literal"`
pair. It was verified not to be a hole: a planted private key under `src/tests/`
produced 5 findings with the allowlist active.

## Item 5: the release gate

`release.yml` had one security step. It now has an explicit, ordered gate:

1. no critical or high advisory without a documented, time-bounded exception
2. the security regression registry validates
3. no secrets in the repository or its history
4. lint, typecheck, build
5. the test suite and the security suite

Cheap checks first, so an obvious problem does not cost a full test run. The audit
gate was tested against a synthetic critical and does exit 1.

Exceptions live in `docs/security/registry-exceptions.md`, which currently records
none. An entry without an expiry is treated as no exception — otherwise the file
becomes a place where gates go to die quietly.

## SEC-046 — service accounts were invisible in the audit log

The most significant finding of the phase, and it arrived sideways.

A new test's fixture passed locally and failed in CI. The reason was printed in
the log *above* the failure:

```
[audit-log-subscriber] failed to write event: PostgresError:
  invalid input syntax for type uuid: "sa:41c84aaf-b100-44be-932d-38887d6a3d32"
```

A machine principal is represented in memory by a user object whose id is the
sentinel `sa:<uuid>`, so routes expecting `request.user` keep working without a
matching user row. The audit subscriber passed that sentinel into
`audit_log.user_id`, which is a **uuid** column. Postgres rejected the insert, the
subscriber's `catch` logged a failure, and the record was lost.

The request succeeded. Nothing failed visibly. A missing audit record is
indistinguishable from a request that never happened.

So **every request authenticated by an API key or an mTLS service account left no
audit trail at all.** The privileged, non-human path was the one that left no
trace — the wrong direction for that gap to point, given that a stolen key is
exactly what an attacker would use quietly.

The fix strips the sentinel, leaves `user_id` null, and records the service
account in `metadata.serviceAccountId`, so the record still identifies who acted
without violating the column type. Two of the five tests fail without the fix.

## Two CI jobs that failed on arrival

**Gitleaks.** `gitleaks/gitleaks-action@v2` requires a paid licence for
organisations and aborts before scanning. Replaced with the CLI in a container.

**Semgrep.** The community rulesets produced 15 findings against `src/`, so
gating on them would mean a permanently red build or a gate that gets switched
off. They now run advisory and report to SARIF; the project ruleset is the
blocking gate. Triage is recorded in the CHANGELOG. The SARIF upload also needed
`security-events: write`, which the job did not have.

Triaging them produced a real finding: the `direct-response-write` hit was a false
positive, but the CSV export it pointed at did not neutralise spreadsheet formula
injection, and several of its columns are attacker-supplied (SEC-045).

## A test that depended on a rate limiter

The CSV export suite seeded its audit row by making a failed login, and asserted
only that the response was `>= 400`. The per-address login budget added in 2.8.0
is 30 per 15 minutes and is shared by the whole suite, so once it was exhausted
the seed started returning **429** — and a 429 is not audited, so the export was
missing the row the test was about. The assertion passed on a row that was never
written.

It failed in CI and passed locally purely because local runs had not yet filled
the budget. The row is now written through the audit subscriber, so the test is
about escaping and nothing else. The negative assertion was also
`!body.includes("'Mozilla")`, which passes when the row is *absent* — a test that
cannot fail.

## A test bug in the fix for SEC-046

Three of the new tests identified the row to assert on by `select().at(-1)`.
Without an `ORDER BY` that is arbitrary, so on a shared audit table it returned
some other test's row — which is how the replay test came to assert
`replayed: false` when the route had computed `true`. Fixed by diffing on row id
against a snapshot, in both this file and the earlier one.

The end-to-end test in that file is documented as **not** proving SEC-046:
`/auth/validate` resolves a key to its owning user, so the principal is a real
uuid and the row is written either way. It is a regression guard on the
surrounding path. The subscriber tests are what prove the finding.

## Item 4 in the plan: the untested behaviour I shipped

Four behaviours had no test, and three of them shipped in the version immediately
before this one:

- `user_login_failed` is emitted on both login routes — **now tested**
- a replayed refresh token is detected and revokes the account's remaining
  credentials, while an unknown token revokes nothing — **now tested**

All 7 new tests were verified by reverting the fixes: with the audit and replay
handling removed, **all 7 fail**.

Writing them surfaced a fourth: my own test had a refresh call passing the token
in the request body, which `/auth/refresh` ignores — it reads a cookie. The test
was asserting on a request that never reached the code under examination. That is
the same failure mode as the 48 unrun tests, one level down.

## Test suites that were not testing what they appeared to

| Suite | Problem | Consequence |
| --- | --- | --- |
| `mfa.test.ts` | never connected Redis | passed only because the limiter failed open |
| `registry.test.ts` | first version asserted against the script's own output | would have passed if the script checked nothing |
| `login-abuse.test.ts` | queried `user_login_failed`; events are stored as `user_login_failed:v1` | matched nothing, so the assertions were vacuous |
| `login-abuse.test.ts` | passed the refresh token in the body | request never reached the code under test |
| whole suite | `node --test` glob one level too shallow | 48 tests silently not running |

Five instances of one pattern, in one phase. The recurring lesson holds: **a test
that does not exercise the real path is worse than no test**, because it converts
an unknown into a false assurance. Each was caught by checking the failure mode
rather than by reading the assertion.

## Packaging defects found while preparing the publish

The plan requires inspecting the tarball before publishing. Doing so turned up
three defects, none of which any existing gate covered.

1. **The package could not be imported.** `dist/index.js` and `dist/index.d.ts`
   shipped with no `main` and no `types`. The `bin` worked, so the CLI was usable
   and the library surface was not. Nothing errored — the package simply could not
   be imported, which is the failure mode nobody notices because no test exercises
   it. Fixed with `main` and `types`, deliberately not `exports`: `exports` is the
   more complete fix and also a breaking change for anyone deep-importing `dist/`
   paths, and 2.6.0 is already published.

2. **The migration guides never shipped.** `docs/` was not in `files` — and was
   not in 2.6.0 either, so this has been true for every release. The instructions
   for the breaking changes in 2.4.0, 2.6.0 and 2.7.0 were GitHub-only, so anyone
   upgrading via npm got the changelog but not the document it referred to.

3. **My own release gate allowed both.** `verify:release` checked version, license
   and repository, which is why it was added in 2.1.0, and a package with no entry
   point and no documentation sailed through. It now also requires `main`/`types`
   to exist on disk, requires the migration docs in `files`, requires
   `dist/tests` to stay excluded, and refuses to publish credential material.

   Verified by reverting: with the three defects reintroduced, the gate reports
   each one by name.

The tarball is otherwise clean: 0 files matching `.env`, 0 certificates or keys,
0 test fixtures, 0 compiled tests. Post-fix it is 715 files, 35 of them
documentation, verified by installing the packed tarball into a clean project and
importing it.
