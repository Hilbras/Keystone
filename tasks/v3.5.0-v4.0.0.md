## Release lifecycle (every version)

For each phase below, follow the roadmap lifecycle in order:

```
Audit → Implementation → Unit Tests → Integration Tests → Security Tests →
Failure/Concurrency Tests → Documentation → CHANGELOG → Git Commit →
GitHub Release → npm Publish → Post-release Verification
```

Commit convention: `feat:`, `fix:`, `security:`, `perf:`, `refactor:`, `test:`, `docs:`, `build:`, `ci:`, `chore:`.

Release branch strategy: `main` → `release/v3.5` … → `release/v4.0` → `RC` → `v4.0.0` → `main`.

## PHASE 1 — Security Hardening → v3.5.1

### §1.1 Webhook SSRF protection — Status: PARTIAL

**Current state:** `webhookDeliveryRefusesPrivateUrl.test.ts` exists; SAML/OIDC `security/enterprise-sso.md` documents private-network blocking and DNS rebinding protection.

**Gap:** Need tests for link-local `169.254.x.x`, IPv6 `::1`/`fc00::`, cloud-metadata ranges, HTTP-vs-HTTPS distinction, redirect protection.

**Tasks:**
1. Audit `src/services/webhooks.ts` for URL validation, DNS resolution, IP classification, private-network blocking, redirect protection, DNS rebinding protection
2. Add tests: `src/tests/security/webhooks/ssrf-private-ip.test.ts`, `ssrf-ipv6.test.ts`, `ssrf-metadata.test.ts`, `ssrf-redirect.test.ts`, `ssrf-http-vs-https.test.ts`

### §1.2 Webhook secret transport — Status: GROSSLY INCOMPLETE

**Current state:** No protocol validation anywhere in webhook creation or delivery. No HTTPS enforcement, no `NODE_ENV` gate.

**Gap:** `production + http = reject`; `development + localhost = allowed`.

**Tasks:**
1. Add `SECURE_WEBHOOK_ONLY` policy: in production, reject `http://` webhook destinations with `400 INVALID_WEBHOOK_URL` at creation time (not delivery time)
2. Dev exception: `KEYSTONE_ALLOW_INSECURE_WEBHOOK=localhost` explicit opt-in env only
3. Document in `docs/security/webhooks.md` and `docs/DEPLOYMENT.md`
4. Test: `src/tests/security/webhooks/https-transport.test.ts` — `http://` rejected in prod, `localhost` HTTP allowed in dev, `https://` always accepted, mixed-case `HtTpS` normalized

### §1.3 Redis rate limiter failure mode — Status: DONE

**Current state:** `src/plugins/rateLimit.ts` — on Redis failure → `limiter: "local"`, bounded counter, metric `rateLimitRedisErrors`, event `rate_limit_triggered`. Documented `docs/security/rate-limiting.md` (v2.8.0).

**Gap:** Verify degraded-mode tests exist and cover bounded fallback.

**Tasks:**
1. Confirm local fallback counter is bounded (not unlimited)
2. Test: `src/tests/security/rate-limiting/failure-mode.test.ts` — Redis unreachable → sensitive endpoints still rate-limited; metric increments; no cap escalation on repeated Redis failure

### §1.4 JWT `kid` validation — Status: DONE (SEC-076)

**Current state:** `src/services/tokens.ts:353` — unknown kid raises; `strictKid.test.ts` covers unknown kid / no kid (legacy path) / foreign `env` kid.

**Gap:** Need cases for `alg:none`, RS256→HS256 swap, expired kid (retired key still in JWKS), revoked key → rejection not fallback.

**Tasks:**
1. Add test cases: `src/tests/security/tokens/strict-kid-extended.test.ts`
2. Document legacy/default-key policy when `kid` is absent

### §1.5 Setup status leakage — Status: GROSSLY INCOMPLETE

**Current state:** `src/routes/setup.ts:145` — GET `/setup/status` returns `{ needsSetup, setupToken }`. The `setupToken` boolean leaks bootstrap state.

**Gap:** Expose only `needsSetup`.

**Tasks:**
1. Change `/setup/status` to return only `{ needsSetup: boolean }`
2. Document in `docs/DEPLOYMENT.md`
3. Test: `src/tests/security/setup/status-response.test.ts` — response contains `needsSetup` only, no `setupToken`

### §1.6 Setup bootstrap race — Status: PARTIAL

**Current state:** `src/routes/setup.ts:270–340` — `/init` reads `hasNoOwners()` then writes owner **outside a transaction**. `ensureDbInitialized()` re-persists config between reads. Concurrent `/setup/init` calls can create two owners.

**Gap:** No transaction, no advisory lock, no atomic invariant.

**Tasks:**
1. Wrap check → register/promote → `updateRole` in a single transaction
2. Add DB advisory lock `keystone:setup:bootstrap` held for the write duration
3. Loser gets `409 CONFLICT "Setup already in progress or complete"`
4. Test: `src/tests/security/setup/bootstrap-race.test.ts` — 20 concurrent `/setup/init` → exactly 1 owner row, 0 duplicates, losers get 409

### Phase gate checklist (v3.5.1)

```
✓ SSRF / private IP / IPv6 / link-local / metadata-range / redirect tests pass
✓ HTTPS-transport rejection (prod) + localhost dev exception pass
✓ Rate limiter fail-closed, bounded local fallback pass
✓ Strict kid + algorithm/revocation cases pass
✓ /setup/status returns needsSetup only
✓ Bootstrap race: 1 owner under 20 concurrent init requests
✓ registry:check, build, lint, typecheck green
```

## PHASE 2 — Distributed Runtime → v3.6.0

### Objective
Make Keystone behave correctly with 1, 2, 10+ instances, multiple regions.

### §2.1 Queue architecture — Status: PARTIAL

**Current state:** `src/services/queue/` provides `BullMQQueue` + `inProcess` drivers. `KEYSTONE_QUEUE_PROVIDER` exists in concept but no startup validation that production never uses in-process.

**Gap:** Production startup must reject `in-process`; development should default to `in-process`.

**Tasks:**
1. Boot-time validation: `NODE_ENV=production` + provider != `bullmq` → ERROR; dev + bullmq without `REDIS_URL` → ERROR
2. Emit structured startup log (ERROR/WARNING/INFO)
3. Test: `src/tests/queue/provider-selection.test.ts`

### §2.2 Queue job model — Status: PARTIAL

**Current state:** `src/services/queue/types.ts` `Job<T>`: `id?, type, payload, attempts?, createdAt?, workerId?, workerHeartbeatAt?`.

**Roadmap requires:** `jobId`, `type`, `tenantId`, `createdAt`, `attempt`, `maxAttempts`, `priority`, `idempotencyKey`, `traceId`.

**Gap:** Missing `tenantId`, `maxAttempts`, `priority`, `idempotencyKey`, `traceId`.

**Tasks:**
1. Extend `Job<T>` with the 5 missing fields (optional, additive)
2. Fill at enqueue: `traceId` from request context, `tenantId` from authenticated tenant, `idempotencyKey` when supplied, `priority` from payload, `maxAttempts` defaulted
3. Persist through BullMQ add/options
4. Test: snapshot of enqueued job → all 11 fields present; both drivers produce identical shapes

### §2.3 Job state machine — Status: PARTIAL

**Current state:** `inProcess.ts` retries up to `attempts` then logs "job failed permanently and was dropped" — no dead-letter queue, `getFailed()` returns `[]`.

**Roadmap:** `pending → processing → completed`; `processing → failed → retrying → processing`; `failed → dead-letter`.

**Gap:** No dead-letter state, no DLQ store, no `drainDeadLetter`/`retryFromDeadLetter`.

**Tasks:**
1. Add `dead-letter` state; `dead_letter_queue` table keyed by `jobId`
2. `Queue` methods: `getFailed(limit)`, `retry(jobId)`, `retryAll()`, `drainDeadLetter(limit)`, `retryFromDeadLetter(jobId)`
3. `getStats()` for both drivers (waiting/active/completed/failed/delayed)
4. Test: `src/tests/queue/state-machine.test.ts` — poison job → retries (cap 30s) → DLQ; manual `retry()` restores; `getFailed`/`getStats` consistent

### §2.4 Distributed locks — Status: DONE

**Current state:** `src/services/lock.ts` — token-verified `SET ... NX PX`, atomic Lua release/renew scripts, `withLock()` try/finally release, `inspectLock()`.

**Gap:** Add `hold(fn)` auto-renewal loop for long operations.

**Tasks:**
1. Add `hold(fn)` that auto-renews lock while `fn` runs
2. Test: renewal survives a 5s pause inside the lock

### §2.5 Worker ownership — Status: PARTIAL

**Current state:** `workerIdentity.ts` defines `HEARTBEAT_INTERVAL_MS=30_000` and lease 120s, **but no heartbeat is emitted**. No Redis last-seen key, no dead-worker cleanup.

**Gap:** Heartbeats declared but never sent; no abandoned-worker detection.

**Tasks:**
1. Emit worker heartbeat to TTL key every 30s (or fold into lock-lease renewal)
2. Implement "find abandoned workers": list expired `keystone:worker:*` keys
3. Test: `src/tests/queue/worker-ownership.test.ts` — kill worker mid-job → lease expires → other instances proceed; `inspectLock` names dead owner

### §2.6 Idempotency — Status: GROSSLY INCOMPLETE

**Current state:** No `IdempotencyKey` mechanism anywhere.

**Gap:** Webhooks, email, workflow execution, token operations, admin actions can all be retried into duplicates.

**Tasks:**
1. `src/services/idempotency.ts`: `claim(tenantId, key, ttlMs)` via Redis `SET ... NX PX`
2. Instrument webhook delivery, refresh-token rotation, admin actions to require claim before mutating
3. Return `409 CONFLICT` with `X-Idempotency-Id` on replay
4. Test: `src/tests/security/idempotency.test.ts` — 100 concurrent same-key requests → exactly 1 mutation

### §2.7 Multi-instance test environment — Status: PARTIAL

**Current state:** `docker-compose.yml` runs a single `keystone` service.

**Gap:** Need 3 `keystone` replicas + Redis + Postgres (+ MySQL per roadmap).

**Tasks:**
1. `docker-compose.multi-instance.yml` — 3 `keystone` replicas sharing DB+Redis, `KEYSTONE_QUEUE_PROVIDER=bullmq`
2. `scripts/concurrency-test.sh` — starts 3 replicas, fires 100 concurrent redemptions/refreshes/deliveries, asserts no duplicates
3. Tests under `src/tests/concurrency/` (see Phase 8 §8.6)

### Phase gate checklist (v3.6.0)

```
✓ production in-process rejection
✓ Job model: all 11 fields
✓ Dead-letter queue + retry API + stats
✓ Lock renewal loop for long ops
✓ Worker heartbeat + abandoned-worker detection
✓ Idempotency service + 409 on replay
✓ 3-instance compose + concurrency harness
```

**Release:** tag `v3.6.0`, npm `keystone@3.6.0`. Release notes: queue changes, production config, Redis requirements, migration requirements, multi-instance behavior.
